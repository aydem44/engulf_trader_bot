# Скилл: Модульные тесты доменной логики (tests-unit)

## 1. Назначение и триггеры

- **Применять когда:** Нужно покрыть тестами чистую логику (например, `calculating_signal()` в `strategy.py`), которая не зависит от API Bybit.
- **НЕ применять:** Для проверок реального API Bybit или состояния позиции (для этого есть `characterization-tests`).

## 2. Предусловия (Inputs)

- Рабочая ветка чиста (`git diff --exit-code` возвращает 0).
- Известна целевая функция (например, `strategy.calculating_signal`).

## 3. Пошаговая процедура (Execution Steps)

### Фаза 1: Инвентаризация ветвлений
1. Выпиши все условия (`if/else`, `match`) в целевой функции.
2. Составь список граничных случаев (например: сигнал LONG, сигнал SHORT, нет сигнала).

### Фаза 2: In-Memory Fake вместо моков
1. Создай файл `tests/unit/test_strategy.py` (если его нет).
2. Не используй `AsyncMock` или `@patch`. Создай простой словарь или объект, который имитирует входные данные (например, обычный `pd.DataFrame`).
3. Напиши тест на каждый граничный случай из Фазы 1.

### Фаза 3: Проверка покрытия
1. Запусти `uv run pytest tests/unit/ -q --cov=strategy --cov-branch --cov-fail-under=100`.
2. Если покрытие меньше 100%, посмотри в отчете, какая ветка (if/else) не была пройдена, и напиши для нее тест.

## 4. Выходные артефакты (Outputs)

- Файл `tests/unit/test_strategy.py` с тестами.

## 5. Ворота готовности (Definition of Done)

1. `uv run pytest tests/unit/ -q --cov=strategy --cov-branch --cov-fail-under=100` возвращает 0.
2. `git diff --exit-code -- strategy.py` возвращает 0 (код приложения не менялся).
3. `ruff check .` и `basedpyright` возвращают 0.

## 6. Стоп-условия и откат

- Если тест выявил баг в `strategy.py` — остановиться и доложить человеку (не исправлять код в этом скилле).
- Если после 3 попыток не удается достичь 100% покрытия — остановиться и доложить.
