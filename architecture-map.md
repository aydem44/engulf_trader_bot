# Архитектурная карта: `engulf_trader_bot`

> Режим исследования: **только чтение**. Исходный код не изменялся.
> Предмет: логика создания, хранения и проверки открытой позиции.
> Дата: 2026-11-03.

---

## 1. Краткое резюме

`engulf_trader_bot` — односимвольный торговый робот для Bybit USDT-perpetual (`MNTUSDT`, `linear`, `15m`). Архитектура линейная: `engulf_trader_bot.py` управляет торговым циклом, `strategy.py` рассчитывает сигнал, `trader.py` работает с биржей, CSV и Telegram, `config.py` и `.env` задают параметры и секреты.

Открытая позиция существует только как локальная переменная `position` внутри `main()`. У неё нет персистентности, отдельного слоя состояния и стартовой сверки с биржей. Биржа фактически является источником истины, но код использует её выборочно: не проверяет `retCode`, не фильтрует записи позиции и не подтверждает филл перед тем, как считать позицию открытой.

В `bot.log` (строки ~41052–41199) виден характерный сбой: бот почти каждую минуту заново «открывает» LONG, затем сразу «закрывает» его по одной и той же старой записи `closed-pnl` (`exit=0.6279`, `PnL=-0.001547`) и сбрасывает состояние. Фактическая позиция при этом не закрывается, а объём на бирже накапливается. Это подтверждает, что дефект сосредоточен в связке «создание → хранение → проверка» позиции.

## 2. Слои архитектуры

Целевая модель — четыре слоя с направлением зависимостей `fetch_klines → strategy → trader`, которые связывает оркестратор `main()`. `config.py` и `.env` — сквозная конфигурация, а не отдельный бизнес-слой.

| Слой | Файл / функция | Ответственность | Запрещено |
|---|---|---|---|
| 1. Интеграция (Data Provider) | `engulf_trader_bot.py:39-72`, `fetch_klines()` | Только получение свечей с Bybit и приведение ответа к DataFrame | Бизнес-логика: индикаторы, тренд, сигналы, решения о входе |
| 2. Доменный (Strategy) | `strategy.py:5-85`, `calculating_signal()` | Чистая логика сигнала: паттерн, направление, SL/TP | Импорт pybit, HTTP-вызовы, CSV, Telegram, состояние позиции |
| 3. Исполнение (Trader) | `trader.py:75-187` | Отправка ордеров, проверка ответов биржи, состояние исполнения, CSV-журнал, Telegram | Решения о входе/выходе и расчёт сигнала |
| 4. Оркестратор | `engulf_trader_bot.py:74-233`, `main()` | Связывание слоёв: `fetch → strategy → trader`; цикл и обработка ошибок | Бизнес-логика сигнала, расчёт индикаторов, владение позицией |

Фактическое состояние не полностью соответствует этой схеме:

- **Data Provider нарушает границу.** `fetch_klines()` (39-72) не только загружает свечи, но и считает `ma_20`/`ma_40`, делает `shift(1)`, merge дневных данных и формирует `is_slowma_lower`. Это доменная логика, которая должна находиться в стратегии.
- **Доменный слой остаётся чистым**, но его контракт зависит от `is_slowma_lower`, подготовленного в Data Provider; часть логики тренда уже вынесена за пределы `strategy.py`.
- **Слой исполнения не владеет позицией.** `trader.py` отправляет ордера, пишет CSV и Telegram, но не предоставляет API для получения позиции или статуса ордера. Поэтому `main()` сам вызывает `session.get_positions()` и `session.get_closed_pnl()` (125-129, 159-163, 191-196), обходя `trader.py`.
- **Оркестратор содержит состояние и побочные эффекты.** `main()` хранит `position`/`last_signal`, принимает решения о переходе в позицию и сам вызывает `log_trade_to_csv()`/`send_telegram_message()`. Это уже не только связывание слоёв.
- **Transport-слой дублируется:** `trader.py` и `engulf_trader_bot.py` создают два независимых pybit-клиента и оба глобально выставляют `HTTP_PROXY`/`HTTPS_PROXY`.

Итог: целевая схема `fetch → strategy → trader` соблюдена лишь частично; состояние позиции распределено между оркестратором и прямыми вызовами биржи, а индикаторы и тренд находятся в слое интеграции.

## 4. Модель состояния открытой позиции

### 4.1. Переменные

`engulf_trader_bot.py:101-102`:

```python
last_signal = None
position = None
```

| Переменная | Тип | Смысл | Изменяется |
|---|---|---|---|
| `position` | `None` или `dict` | Локальный снимок открытой позиции | строки 130, 164, 221 |
| `last_signal` | `None`, `1`, `-1` | Антидребезг повторного входа в рамках процесса | строки 131, 165, 222 |
| `last_heartbeat` | `float` | Периодический heartbeat | строки 103, 119 |

### 4.2. Поля `position`

| Поле | Источник | Смысл | Ограничение |
|---|---|---|---|
| `side` | локальный сигнал | `'long'`/`'short'` по мнению бота | не сверяется с `side`/`positionIdx` биржи |
| `entry` | `get_positions().list[0].avgPrice` | средняя цена входа | строковое, может быть `""` до филла |
| `qty` | `list[0].size` | размер позиции | может быть `"0"`; не используется при закрытии |
| `opened_at` | `list[0].createdTime` | время создания позиции, не текущего входа | может быть старым или пустым |

### 4.3. Жизненный цикл

```
FLAT (position=None, last_signal=None)
  │ signal=±1, last_signal != signal, not position
  ▼
OPENING: POST /v5/order/create
  │ if order:                         ← проверяется только truthiness
  │   get_positions().list[0]         ← без проверки пустоты/размера/стороны
  │   position = {...}                ← сразу, без подтверждения филла
  │   last_signal = signal
  ▼
OPEN
  │ каждый цикл: get_closed_pnl(startTime=position['opened_at'], limit=1)
  │ if records:                      ← любая запись, без сверки с позицией
  │   CSV + Telegram; position=None; last_signal=None
  ▼
FLAT
```

Характерные свойства текущей модели: нет состояний `OPENING`/`UNKNOWN`; нет персистентности; нет сверки с биржей при старте и после исключений; закрытие определяется наличием любой записи `closed-pnl`, а не отсутствием позиции; `last_signal` — только процессный антидребезг.

### 4.4. Источник истины

| Вопрос | Текущий ответ | Фактический источник |
|---|---|---|
| Есть ли открытая позиция? | `position is not None` | `GET /v5/position/list` с фильтром `size > 0` |
| Ордер исполнен? | `if order:` | `retCode == 0` + статус ордера + размер позиции |
| Когда открыта? | `createdTime` позиции | время ордера/исполнения |
| Когда закрыта? | любая запись `closed-pnl` после `opened_at` | `size == 0` + сопоставленная запись `closed-pnl` |
| Фактический объём? | `POSITION_SIZE` в CSV, `size` в state | `size`/`cumExecQty` после филла |
| Переживает рестарт? | нет | персистентность и/или реконсиляция |

## 5. Внешние HTTP-контракты

### 5.1. Bybit REST v5

Базовый URL задаёт pybit; в коде `testnet=False` (`trader.py:27-30`, `engulf_trader_bot.py:32-35`).

| Метод pybit | HTTP | Параметры | Используемые поля | Вызов |
|---|---|---|---|---|
| `get_kline` | `GET /v5/market/kline` | `category`, `symbol`, `interval`, `limit` | `datetime, open, high, low, close, volume, turnover` | `engulf_trader_bot.py:42-74` |
| `get_instruments_info` | `GET /v5/market/instruments-info` | `category`, `symbol` | `tickSize`, `qtyStep`, `minOrderQty` | `trader.py:44-50` |
| `get_wallet_balance` | `GET /v5/account/wallet-balance` | `accountType='UNIFIED'`, `coin` | `result.list[0].coin[0].equity` | `trader.py:65` |
| `place_order` | `POST /v5/order/create` | `category`, `symbol`, `side`, `qty`, `orderType='Market'`, `marketUnit='baseCoin'`, `takeProfit`, `stopLoss` | `retCode`, `retMsg`, `orderId`, `orderLinkId` | `trader.py:83-92` |
| `get_positions` | `GET /v5/position/list` | `category`, `symbol` | `side`, `size`, `avgPrice`, `createdTime`, `updatedTime`, `positionIdx` | `engulf_trader_bot.py:125-128, 159-162` |
| `get_closed_pnl` | `GET /v5/position/closed-pnl` | `category`, `symbol`, `startTime`, `limit=1` | `avgEntryPrice`, `avgExitPrice`, `closedPnl`, `qty`, `side`, `createdTime`, `orderId` | `engulf_trader_bot.py:191-196` |

### 5.2. Telegram и прокси

`send_telegram_message` выполняет `POST https://api.telegram.org/bot<TOKEN>/sendMessage` с form-data `chat_id`, `text`, `parse_mode='HTML'` (`trader.py:169-187`). Токен и chat_id читаются из `.env`; при отсутствии — warning и no-op.

`HTTP_PROXY`/`HTTPS_PROXY` формируются из `PROXY_*` и глобально выставляются в `os.environ` в обоих модулях (`trader.py:16-23`, `engulf_trader_bot.py:24-29`), поэтому влияют и на запросы к Telegram.

### 5.3. Разрывы контрактов

- `place_market_order` не проверяет `retCode`/`retMsg`; `main` считает успехом любой truthy-ответ.
- `get_positions().result.list` может быть пустым сразу после market-ордера; `list[0]` даёт `IndexError`.
- Список позиций может содержать нулевые и hedge-записи (`positionIdx=1/2`); `list[0]` берётся без фильтра.
- Числовые поля (`avgPrice`, `size`, `qty`, `closedPnl`, `createdTime`) приходят строками.
- `closed-pnl` фильтруется по `startTime`, но не сопоставляется с текущим ордером, `side`, `qty` или `orderId`; `limit=1` возвращает последнюю запись.
- `createdTime` позиции — время её создания, а не текущего входа; при усреднении `avgPrice`/`size` меняются, а `createdTime` остаётся старым.
- Режим позиций не задаётся: код предполагает one-way mode, но не проверяет `positionIdx`.
- `orderLinkId` не задаётся, поэтому повтор после таймаута создаёт новый ордер.
- Partial fill/partial close не моделируются; TP/SL привязаны к ордеру без `tpslMode`.

## 6. Зона риска

### 6.1. Критические дефекты

| ID | Дефект | Где | Последствие |
|---|---|---|---|
| R1 | Ложное закрытие по старой записи `closed-pnl`: `startTime=opened_at`, `limit=1`, без сверки `side`/`qty`/`orderId` и без проверки `size == 0` | `engulf_trader_bot.py:190-222` | state сбрасывается при открытой позиции; следующий цикл снова входит. В `bot.log:41052-41199` — ~15 повторных входов, каждый раз одна и та же запись `exit=0.6279`, `PnL=-0.001547` |
| R2 | `get_positions().list[0]` без проверки пустоты, `size > 0`, `side`, `positionIdx` | `engulf_trader_bot.py:125-130, 159-164` | `IndexError` после уже отправленного ордера; state остаётся `None` → повторный ордер. Либо в state попадает чужая/нулевая запись |
| R3 | Нет персистентности и стартовой реконсиляции | `engulf_trader_bot.py:101-102` | рестарт «забывает» позицию; возможен второй вход |
| R4 | Нет подтверждения исполнения: `if order:` вместо `retCode == 0` и проверки филла | `engulf_trader_bot.py:124, 158`; `trader.py:83-98` | позиция фиксируется до фактического исполнения |
| R5 | Нет идемпотентности: `orderLinkId` пустой, `orderId` не сохраняется до side effect | `trader.py:83-92` | исключение после `place_order` приводит к дублю ордера |
| R6 | Широкий `except Exception` после side effect; лог на уровне INFO, повтор через 60 с | `engulf_trader_bot.py:228-230` | дублирование ордеров, причина ошибки скрыта, реконсиляции нет |

### 6.2. Высокие риски

| ID | Дефект | Где | Последствие |
|---|---|---|---|
| R7 | `opened_at` = `createdTime` позиции, а не текущего входа | `engulf_trader_bot.py:130, 164` | старые `closed-pnl` проходят фильтр; `startTime` может быть пустым |
| R8 | При закрытии не проверяется фактический размер позиции | `engulf_trader_bot.py:190-222` | ложное «закрыто» при частичном закрытии или старой записи |
| R9 | `qty`/`entry` не используются для сверки; в CSV при открытии пишется `POSITION_SIZE` | `engulf_trader_bot.py:136, 170`; `trader.py:142-162` | журнал и Telegram расходятся с биржей |
| R10 | Hedge mode и `positionIdx` не учитываются; сторона берётся из сигнала | `engulf_trader_bot.py:130, 164` | работа не с той ногой позиции, неверный PnL |
| R11 | Частичные филлы/закрытия не моделируются | вся модель `position` | `qty` устаревает, TP/SL и `closed-pnl` относятся к части позиции |
| R12 | `last_signal` сбрасывается в `None` после закрытия | `engulf_trader_bot.py:222` | тот же сигнал может сразу открыть новую позицию |
| R13 | `position['opened_at']` = `createdTime` из `Get Position Info`; по документации Bybit это timestamp первого создания позиции по символу, а не время текущего входа. При накоплении позиции значение не обновляется, поэтому в `get_closed_pnl(startTime=opened_at, limit=1)` уходит устаревшее окно (только `startTime` → 7 дней) и повторно возвращается старая запись | `engulf_trader_bot.py:167, 205, 241` | конкретизация R7 и механизм R1: ложное закрытие по старой `closed-pnl`, повторные входы; реальное закрытие позже 7 дней может не попасть в окно |

### 6.3. Средние риски и наблюдаемость

- `log_trade_to_csv` падает на пустом `avgPrice` (`float("")`) уже после установки `position` (`trader.py:156`).
- `if pnl` отбрасывает `pnl == 0`; `if tp/sl` отбрасывает нулевые значения (`trader.py:157-160`).
- Два независимых pybit-клиента и глобальная мутация прокси (`trader.py:16-30`; `engulf_trader_bot.py:24-35`).
- Нет retry/backoff и учёта rate limit; цикл фиксированные 60 с (`engulf_trader_bot.py:223`).
- Нет тестов и dry-run/testnet-переключателя (`testnet=False` жёстко).
- `STOP_LOSS_PCT`/`TAKE_PROFIT_PCT` в `config.py` и `ma_fast`/`ma_slow` в `calculating_signal` не используются.

### 6.4. Радиус поражения

| Потребитель | Эффект ошибки |
|---|---|
| Реальная позиция на Bybit | дублирующие входы, накопление объёма, отсутствие управления после ложного закрытия |
| `trades.csv` (`$CSV_FILE`) | неверные `qty`/`entry`, фиктивные или пропущенные закрытия |
| Telegram | ложные уведомления об открытии/закрытии |
| `bot.log` | шум и повторяющиеся события, причина скрыта в `except` |
| Будущая аналитика/PnL | искажённая статистика из-за расхождения state и биржи |

Внешних импортов `engulf_trader_bot` нет, поэтому изменение его внутренних функций не ломает другие модули.

### 6.5. Архитектурные риски и состояние позиции

| ID | Риск | Проявление |
|---|---|---|
| A1 | Бизнес-логика в Data Provider | `fetch_klines()` считает `ma_20`/`ma_40`, `shift(1)`, merge и `is_slowma_lower` (39-72). Стратегия получает готовый признак, а не сырые свечи; изменение data-слоя незаметно меняет сигнал. |
| A2 | Оркестратор напрямую работает с биржей | `main()` вызывает `session.get_positions()` и `session.get_closed_pnl()` (125-129, 159-163, 191-196), минуя `trader.py`. Нет единого места проверки `retCode`, нормализации и фильтрации ответов. |
| A3 | У состояния позиции нет слоя-владельца | `position` — локальный dict в `main()`, а `trader.py` не предоставляет API позиции/ордера. Создание, хранение и проверка позиции распределены между оркестратором и прямыми вызовами pybit. |
| A4 | Один dict смешивает разные сущности | `position` одновременно означает «ордер отправлен», «филл получен», «позиция открыта» и «позиция закрыта». Нет явных состояний `OPENING/OPEN/UNKNOWN` и инварианта «одна позиция на символ». |
| A5 | Состояние фиксируется до подтверждения филла | `position` создаётся сразу после `if order:` из `list[0]`, без проверки `size > 0`, `side`, `positionIdx` и принадлежности текущему `orderId`. Возможен учёт чужой, ручной или нулевой позиции. |
| A6 | Нет персистентности и стартовой реконсиляции | `position`/`last_signal` живут только в памяти (101-102). Рестарт или исключение после `place_order` оставляют реальную позицию без локального учёта. |
| A7 | Исключение после side effect не откатывает состояние | Если после успешного `place_order` возникает `IndexError` на `list[0]` или ошибка CSV, `position` остаётся `None`, а ордер уже исполнен; следующий цикл повторяет вход. |
| A8 | `last_signal` не является состоянием позиции | Это процессный антидребезг: после рестарта он `None`, после закрытия сбрасывается, поэтому не защищает от повторного входа и не отражает реальную позицию. |
| A9 | Побочные эффекты исполнения в оркестраторе | `main()` сам вызывает `log_trade_to_csv()` и `send_telegram_message()`, хотя по целевой модели это зона `trader.py`; момент и формат записи не централизованы. |
| A10 | Нет проверки принадлежности позиции текущему входу | `side` берётся из сигнала, а `entry`/`qty` — из первой записи `get_positions`; при hedge mode, ручной позиции или остатке от прошлой сделки состояние может описывать не тот объект. |
| A11 | Дублирование transport-слоя | Два pybit-клиента и глобальные `HTTP_PROXY`/`HTTPS_PROXY` в `main` и `trader`; ответственность за сетевой слой размыта. |

## 7. Потребители и побочные эффекты

## 9. Возможные направления исправления

Логика позиции тяготеет к явной state machine: `FLAT` → `OPENING` → `OPEN` → `FLAT`, с отдельным `UNKNOWN` для таймаутов и ошибок. В такой модели вход не считается открытым до подтверждения филла, а новый вход запрещён, пока предыдущий ордер не завершён.

Основной принцип — биржа как источник истины. Позиция читается из `GET /v5/position/list` с фильтром по `symbol`, `size > 0` и `positionIdx`; локальный `position` становится кэшем, производным от этого ответа. При старте и после исключений полезно выполнять реконсиляцию: если на бирже есть позиция, бот принимает её, а не открывает новую.

Для входа важно разделять отправку ордера и его исполнение: проверять `retCode`, передавать стабильный `orderLinkId`, при необходимости опрашивать статус ордера и дожидаться `size > 0`. Закрытие логично фиксировать только при `size == 0` и наличии сопоставленной записи `closed-pnl` (по `side`, `qty`, `orderId`/времени), а не по факту любой записи после `startTime`. `createdTime` позиции не подходит на роль времени текущего входа.

Персистентность состояния (например, небольшой JSON с `order_id`, `order_link_id`, `side`, `opened_at`) уменьшает риск дубля после рестарта, но её допустимость требует отдельного согласования. В любом случае все числовые поля нужно нормализовать (`Decimal`), а стороны — приводить к единому виду (`Buy`/`Sell` ↔ `long`/`short`).

## 10. Признаки корректной работы

Корректная реализация характеризуется следующими наблюдаемыми свойствами:

- один сигнал приводит к одному ордеру; в логе нет повторяющихся «позиция открыта» каждые 60 секунд при неизменном сигнале;
- `get_positions` после входа показывает `size > 0`, а локальное состояние совпадает с биржей;
- при закрытии по TP/SL сначала фиксируется `size == 0`, затем появляется одна запись `closed` в CSV и одно Telegram-уведомление;
- рестарт при открытой позиции не приводит ко второму входу;
- `closed-pnl` сопоставляется с текущей позицией, а не с любой исторической записью;
- `startTime` не бывает пустым или невалидным;
- CSV при открытии содержит фактический `size`, а не только `POSITION_SIZE`;
- ошибки `retCode != 0`, пустой `list`, `size="0"` и hedge mode обрабатываются предсказуемо.

Регрессионный ориентир — `bot.log:41052-41199`: повторяющиеся входы и ложные закрытия с одной и той же записью `exit=0.6279`, `PnL=-0.001547`.
